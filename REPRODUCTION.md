# Reproduction Guide

This repository is the ROS 1 Noetic implementation for the paper
"VLM-empowered Multi-Mode System for Efficient and Safe Planetary Navigation"
(arXiv:2506.16703, IROS 2025).

The paper evaluates a closed-loop planetary rover navigation stack in Gazebo:

- Mode 1, efficient flat-terrain navigation: shortest/smoothed path and pure
  pursuit control.
- Mode 2, safe rocky-terrain navigation: 2D hazard map, A* local planning, and
  lower tracking speed.
- Mode 3, conservative challenging-terrain navigation: GPU elevation/cost map,
  A* local planning, and conservative tracking speed.
- VLM mode selector: RGB/depth terrain observation is classified as flat, rocky,
  or challenging and published as `/navigation_mode`.

The target paper metrics are:

- Single-mode traversal: flat, rocky, and challenging terrain with success rate
  and average traversal time.
- Multi-mode traversal: mixed terrain, comparing a conservative-only baseline
  against VLM-driven mode switching.
- Reported paper result: multi-mode traversal uses 602.6 s over 411.8 m versus
  conservative-only 1081.7 s over 413.7 m, a 79.5% efficiency improvement by
  the paper's definition.

This checkout includes a working ROS 2 Humble port under `ros2/`. It runs the
full multi-mode stack **headlessly** on Ubuntu 22.04 + ROS 2 Humble — no Gazebo,
no `elevation_mapping_cupy`, no CUDA. The rover pose is simulated kinematically
and the perception maps are derived from the terrain heightmap.

```text
image_to_map  -> /mode1/occupancy_grid  -> map_server -> global_planner
hazard_mapper -> /mode2|mode3/occupancy_grid -> local_planner
terrain_image_publisher -> vlm_mode (OmniLRS Qwen3-VL) -> /navigation_mode
path_follower -> /cmd_vel -> pose_simulator -> /pose_with_covariance
```

### Python environment

Use the **system** Python 3.10 (`/usr/bin/python3`), not conda's 3.13 — ROS
Humble's `rclpy` is compiled for 3.10 and conda cannot import it. Also, a
NumPy 2.x in `~/.local` breaks the apt `scipy`/`cv_bridge` (NumPy 1.x ABI), so
pin NumPy 1.x and install the VLM client libs:

```bash
/usr/bin/python3 -m pip install --user "numpy==1.24.4" openai httpx
```

(conda must be kept out of `PATH` during build/run so `python3` resolves to
`/usr/bin/python3`.)

### Run

```bash
source install/setup.bash
ros2 launch mars_navigation_ros2 smoke_stack.launch.py            # VLM mode switching
ros2 launch mars_navigation_ros2 smoke_stack.launch.py use_vlm:=false  # manual mode
```

Start/goal are launch args. The default `(-20.0, 0.0)` → `(20.0, 0.0)` corridor
crosses the **synthesised mixed heightmap** (`docs/picture/terrain/mixed_terrain_hm.png`)
from west to east along `y = 0`, so a single run moves through every terrain
segment in order:

```bash
ros2 launch mars_navigation_ros2 smoke_stack.launch.py \
    start_x:=-20.0 start_y:=0.0 goal_x:=20.0 goal_y:=0.0
```

```text
flat        x <  -12   (Mode 1, 2.0 m/s)
rocky       [-12, -6)  (Mode 2, 0.8 m/s, scattered rocks)
challenging [-6,  +6)  (Mode 3, 0.5 m/s, smooth ~15.8 deg ridge)
flat        x >= +6    (Mode 1, 2.0 m/s)
```

The real Mars Yard has no region where the modes differ in *capability* (Mode 1's
2° base map and Mode 3's cost map agree on what is traversable), so the mixed
heightmap is generated by `ros2/tools/generate_mixed_terrain.py` to give the
modes genuinely different terrain to handle. The kinematic `pose_simulator` adds
a slope-based rollover model (mode-specific slope limits) so that a mode's
success on the ridge reflects its actual capability rather than just its speed:
a mode rolling over is a hard failure, exactly the paper's success-rate axis.
`terrain_image_publisher` tracks `/pose_with_covariance` and publishes the
flat/rocky/challenging image matching the rover's current `x`, so the VLM
switches mode in sync with the terrain.

### Automated evaluation

```bash
cd ros2
bash mars_navigation_ros2/scripts/run_experiments.sh mode1   # single mode 1..3, vlm, or all
```

Each run launches the stack headlessly, collects metrics with
`evaluate.py`, and writes `runs/<name>/{metrics.json,trajectory.csv,stack.log}`.
Recorded results (start `(-20,0)`, goal `(20,0)`, arrival radius 2 m), with the
slope-based rollover model (Mode 1 limit 8°, Mode 2 limit 12°, Mode 3 limit
40°) so the modes differ by *capability*, not just speed:

| run | success | reason | time | distance | avg speed |
| --- | --- | --- | --- | --- | --- |
| mode1 (flat, 2.0 m/s) | ❌ | rollover (ridge 8.1° > 8°) | 7.70 s | 14.96 m | 1.943 m/s |
| mode2 (rocky, 0.8 m/s) | ❌ | rollover (ridge 13.3° > 12°) | 20.20 s | 15.77 m | 0.781 m/s |
| mode3 (challenging, 0.5 m/s) | ✅ | goal reached | 79.20 s | 39.07 m | 0.493 m/s |
| vlm (multi-mode) | ✅ | goal reached | 42.44 s | 38.53 m | 0.908 m/s |

The ~15.8° smooth ridge is the capability-differentiating terrain. Mode 1 rolls
over on its outer flank (8.1° vs an 8° limit) and Mode 2 on the steeper inner
slope (13.3° vs a 12° limit), so both fail before the goal; only the slope-aware
Mode 3 crosses it. The VLM run classifies flat → rocky → challenging → flat and
switches `Mode 1 → 2 → 3 → 1`, engaging Mode 3 just before the ridge and reaching
the goal in 42.44 s — a ~46% time saving over the conservative-only Mode 3
baseline (79.20 s), reproducing the paper's multi-mode efficiency result while
succeeding where the single fast/safe modes fail. Per-mode breakdown is in
`docs/reproduction/metrics_summary.md`.

Reproduction figures, the traversal video, and the raw VLM dialogue are under
`docs/reproduction/` (`figures/`, `video/traversal.mp4`, `vlm_dialogue.txt`),
generated by `ros2/tools/generate_artifacts.py`.

The `vlm_mode` node strips proxy env vars before calling the local endpoint
(a `socks://` `ALL_PROXY` otherwise crashes httpx). Default endpoint:

```text
QWEN_VL_BASE_URL=http://127.0.0.1:22002/v1
QWEN_VL_MODEL=/home/lry/OmniLRS/deploy/qwen3vl/models/Qwen3-VL-8B-Instruct-AWQ-4bit
```

### Porting notes (gotchas fixed)

- `image_to_map.py` faithfully ports the original `image2map_initialize.py`
  pipeline (`calculate_accessibility_map` → `filter_small_connected_regions` →
  `connect_regions_via_distance` → morphology → normalize). A naive
  `np.gradient` slope pass fragments the free space into salt-and-pepper cells,
  which the global A* (with its 5×5 aggregation) cannot traverse.
- `global_planner` start/goal are **scalar** params: a list of launch
  substitutions (`[start_x, start_y]`) gets flattened to a single string and
  rejected by rclpy as a `DOUBLE_ARRAY`.
- The `global_planner` A* requires start and goal inside free space; the
  original corner defaults `(-22,-22)`/`(20,20)` both land in obstacle regions.
- `local_planner` must replan as the rover *moves*, not only when the local goal
  changes. Its local map is re-centred on the rover every tick, so a path cached
  from an earlier pose drifts out of the window and stalls the pure-pursuit
  follower a couple of metres short of the goal (the rover just sits there).
- The VLM classifier is *event-driven*: it runs the moment a new terrain image
  arrives (see `vlm_mode.py::_image_cb`) instead of on the paper's 5 s timer. A
  timer round-trip can leave the rover in Mode 2 for a whole extra interval after
  it crossed into the challenging segment — long enough to roll over on the ridge
  before Mode 3 engages. The `evaluation_interval` timer survives only for the
  standalone `image_file` fallback.

### Verify

```bash
ros2 topic echo /navigation_mode
ros2 topic echo /pose_with_covariance --field pose.pose.position
ros2 node list
```

Expected: `/navigation_mode` switches `Mode 1` (flat) → `Mode 2` (rocky) →
`Mode 3` (challenging) → `Mode 1` (flat) as `terrain_image_publisher` follows
the rover's `x`-position across the mixed heightmap, `path_follower` switches
speed 2.0 / 0.8 / 0.5 m/s accordingly, and the pose drifts toward `(20.0, 0.0)`.

## 1. Required Platform

Use Ubuntu 20.04 with ROS Noetic. This code is not a ROS 2 Humble workspace.

The current checked machine was verified as Ubuntu 22.04 with ROS 2 Humble
only, so native catkin reproduction is blocked there. Use a Ubuntu 20.04/Noetic
machine or the container entry below.

Required ROS/Gazebo components:

```bash
source /opt/ros/noetic/setup.bash
sudo apt update
sudo apt install -y python3-catkin-tools ros-noetic-desktop-full ros-noetic-gazebo-ros ros-noetic-gazebo-ros-control ros-noetic-gazebo-plugins ros-noetic-rqt ros-noetic-rqt-gui ros-noetic-rqt-gui-py ros-noetic-rviz ros-noetic-pcl-ros ros-noetic-pcl-conversions ros-noetic-tf-conversions ros-noetic-rtabmap-ros ros-noetic-compressed-image-transport ros-noetic-controller-manager ros-noetic-joint-state-controller ros-noetic-diff-drive-controller
```

For `elevation_mapping_cupy`, follow the upstream Noetic/CUDA instructions:

```text
https://leggedrobotics.github.io/elevation_mapping_cupy/getting_started/installation.html
```

Container entry from an Ubuntu 22.04 host:

```bash
./tools/run_noetic_container.sh
```

The first run builds `mars-navigation:noetic`, so it will download ROS Noetic
and Gazebo dependencies. Mode 3 uses CuPy/GPU elevation mapping; for hardware
acceleration the host should have a working NVIDIA driver and Docker GPU
runtime. GUI/Gazebo forwarding requires a working Docker X11 setup on the host.

## 4. Launch Sequence

The GUI provides grouped workflows, but the command-line sequence below is the
minimum reproducible path and is easier to debug.

Start simulation and visualization:

```bash
roslaunch leo_erc_gazebo leo_marsyard.launch
roslaunch leo_erc_viz rviz.launch
```

Initialize the map server and global map/path:

```bash
roslaunch globalmap_server map_server.launch
roslaunch globalmap_server initializemap_client.launch
./nav_framework/global_initializer/scripts/global_map_initialize.sh
roslaunch globalmap_server initialize_globalpath_client.launch
./nav_framework/global_initializer/scripts/global_planning.sh
```

In RViz, publish a goal with `2D Nav Goal`. The global path should appear on
`/map_server/global_path_updated`.

Start local mapping, planning, and control:

```bash
roslaunch hazard_detection detect_and_mapping.launch
roslaunch elevation_mapping_cupy mapping_leo.launch
roslaunch globalmap_server getlocalmap_client.launch
roslaunch globalmap_server updatemap_client.launch
./planning/global_path_optimizer/scripts/global_path_optimize.sh
./planning/local_planner/scripts/local_planner.sh
roslaunch c_pursuit_ctrl c_pursuit.launch
```

Choose mode manually for deterministic reproduction:

```bash

```

Or run VLM-based mode switching. The default is the local OmniLRS Qwen3-VL

## 5. What To Verify

Core topics:

```bash
rostopic list | grep -E 'navigation_mode|map_server|local_planner|trajectory_ctrl|cmd_vel'
rostopic echo /navigation_mode
rostopic hz /cmd_vel
rostopic hz /map_server/global_map
rostopic hz /local_planner/local_path
```

Expected mode behavior:

- `Mode 1`: controller follows `/trajectory_ctrl/global_path_updated`; local
  map/planner can be inactive.
- `Mode 2`: `hazard_detection` publishes `/mode2/occupancy_grid`; local planner
  publishes `/local_planner/local_path`.
- `Mode 3`: `elevation_mapping_cupy` publishes `/mode3/occupancy_grid`; local
  planner publishes `/local_planner/local_path`.

For paper-style reproduction, log one run per terrain/mode pair:

```bash
mkdir -p runs
rosbag record -O runs/mode1_flat.bag /navigation_mode /cmd_vel /pose_with_covariance /map_server/global_path_updated /local_planner/local_path /mode2/occupancy_grid /mode3/occupancy_grid
```

The paper tables require success/failure, traversal time, and traversal
distance. These are not currently computed by a bundled evaluator, so extract
them from `/pose_with_covariance` and collision/failure observations in Gazebo.
